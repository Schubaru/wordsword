## Blockers

### B1. Sign-in codes have no delivery, and the code is printed on screen · Guideline 2.1(a) · `Wordsword/AccountFlow.swift:356`

**What:** `Auth.sendCode` generates the code locally ([Auth.swift:122](../Wordsword/Auth.swift:122))
and `AccountFlow` renders it: `"No server yet — your code is \(pending)"`. Not inside `#if DEBUG`.
Confirmed again in today's Release binary by `strings` on the compiled executable.

**Why it blocks:** 2.1(a), fetched today — "include demo account info **(and turn on your back-end
service!)** if your app includes a login."

**Why I did not fix this.** Deleting the label is a two-second edit and it would be the wrong one.
Without delivery, removing the display does not produce a working login — it produces a screen that
asks for a code no one can obtain, which is a harder 2.1 rejection than the honest placeholder and
strands every real user. The skill's rule against disabling code to make a check pass exists for
exactly this. **This blocker needs infrastructure, not a diff.**

**Your options, cheapest first:**

1. **Sign in with Apple.** Native, no backend, no codes, no delivery vendor, no deliverability
   problems. Costs the Apple Developer account you need anyway (B4) plus the capability in
   `project.yml`, and it changes the sign-up screen. **This is the only option that gets you to
   submission without standing up a service**, which is why I list it first — but it is a product
   change, so it is decision §2 below, not something I did.
2. **A transactional email/SMS provider** behind a small server (Supabase Auth, Resend, Postmark,
   Twilio). Keeps your current email-or-phone flow exactly as designed — the code already isolates
   this to three `// stub:` bodies, so the app-side change is genuinely small. Costs a service, an
   account, keys kept out of the binary, and — for SMS — per-message money and carrier deliverability.
3. **Cut accounts from v1 after all.** Still available, and still the smallest total change. You
   ruled it out; noting it once so the trade-off stays visible, not to relitigate it.

Whichever you choose, the flow already handles the states around it (resend, wrong code, unknown
account, crossovers), so the work is delivery, not UI.

**Advanced this run:** I wrote the policy — [privacy-policy-draft.md](privacy-policy-draft.md) —

## Fixed automatically

### 1. Account deletion — `Auth.swift`, `SettingsView.swift`, `WordswordApp.swift`

**Why:** closes B2. Guideline 5.1.1(v), verbatim from today's fetch — "If your app supports account
creation, you must also offer account deletion within the app." Now unambiguously triggered.

`Auth.deleteAccount()` clears the identifier, username, signed-in flag, and any pending code, from
memory and from `UserDefaults`. Ordering matters and is commented: `username`'s `didSet` writes an
empty string back to the store, so the `removeObject` calls come after the assignments or the keys
survive as `""` rather than absent.

**Saved words are deliberately kept.** They are local content that was never account-derived, and
Settings already has its own "Clear all my words" control. Deleting an account should not silently
take a library with it. This was flagged in run 1 as a decision I would not make silently — it is
made visibly here, it is stated in the confirmation dialog before anything happens, and it is a
one-line change if you disagree.

**Verified three ways, not assumed:**

1. **A runnable check.** `Auth.selfCheck()` ([Auth.swift:176](../Wordsword/Auth.swift:176)) runs
   against a throwaway `UserDefaults` suite and asserts deletion clears memory and disk, that a
   **relaunch does not resurrect the account**, and that the **legacy-onboarding migration does not
   either** — that last one being the specific path that could have brought it back, since `init`
   treats a saved identifier as proof of an account.
2. **The check demonstrably runs.** A passing assert is indistinguishable from one that never
   executes, so I inverted one assertion, rebuilt, and confirmed the app died on launch; reverted,
   rebuilt, confirmed it survives. The harness is live, not decorative.
3. **The UI renders.** Drove the existing snapshot tour and inspected `24-settings.png`: the row
   sits under Sign out in the "You" section, styled destructive, with the section outline closing
   correctly.

### 2. `Auth.init(defaults:)` — a latent injection bug, fixed in passing

`private let defaults = UserDefaults.standard` meant the `defaults:` parameter was read-only in
practice: a caller passing its own suite got **reads from it and writes to `UserDefaults.standard`.**
No shipping impact — nothing passed a custom suite — but it made the seam a trap, and the
self-check above needs it to work. Now `self.defaults = defaults`.

### 3. Settings footer wording

The footer under the "You" section said "Signing out keeps every word on this phone." With a red
**Delete account** now sitting directly above it, saying only "signing out" invites the reader to
assume deletion behaves the opposite way. Reworded to cover both actions.

## Needs your decision

1. **When delivery ships, three declarations change together.** Right now the account identifier
   never leaves the device, so an empty `NSPrivacyCollectedDataTypes` and a labels draft of "Data
   Not Linked to You" are both accurate. The moment codes are actually delivered, your email
   address or phone number is transmitted, and all three must be updated **in the same build**:
   - `Wordsword/PrivacyInfo.xcprivacy` → add collected data types
   - App Privacy labels → **Contact Info (Email Address / Phone Number), linked to you**
   - [privacy-policy-draft.md](privacy-policy-draft.md) §2 → name the provider
   Mismatches between the manifest and the labels are caught automatically and rejected. I have not
   pre-filled any of it, because the right values depend on the vendor you pick in B1.

2. **Sign in with Apple instead of codes?** See B1 option 1. It removes the entire delivery problem
   and, with it, most of decision 1 — Apple's private relay means you may never receive a real email
   address at all. It also changes your sign-up screen and drops the phone-number path, which your
   `Contact` type was clearly designed for. Genuinely a product call; I flag it because it is the
   difference between "submit this month" and "stand up a service first."

3. **The reviewer needs a working account.** 2.1(a) requires demo account info when the app has a
   login. Once delivery exists, either create a real demo account whose inbox you control, or use a
   fixed test identifier that always accepts a known code. Draft review notes are in Next steps.
